# 02 · Scoping and Feature Prioritization

Scope creep kills projects. This page shows how to decide **what to build and what to drop**.

## 1. MoSCoW Method

| Level | Meaning | Rule of thumb |
|-------|---------|---------------|
| **M**ust | Project fails without it | ~50–60% of effort |
| **S**hould | Important, adds big value | ~25–30% of effort |
| **C**ould | Nice to have | Only if time remains |
| **W**on't | Intentionally excluded (this release) | Write it down! |

### Example (Mini Shell)

| Level | Feature |
|-------|---------|
| Must | Prompt loop, run external commands (`fork`+`exec`+`wait`), `cd`, `exit` |
| Should | Output redirection `>`, `<`, single pipe `|`, background `&` |
| Could | Command history, multiple pipes, tab completion |
| Won't | Scripting language, job control with `fg`/`bg` |

## 2. The Vertical Slice Principle

❌ Don't build "all input parsing, then all algorithms, then all output."
✅ Build **one thin slice** from input → logic → output first, then widen.

```
Week 1:  input(1 case) → FCFS → print table          ← works end to end
Week 2:  add SJF, RR, metrics, more input formats
Week 3:  add charts, step mode, tests
```

## 3. Time Estimation Cheat Sheet (with AI help, for beginners)

| Task | Typical time |
|------|--------------|
| Learn one OS concept well enough to implement | 3–6 hours |
| Implement one scheduling/replacement algorithm | 2–4 hours |
| Understand + explain AI code for that algorithm | 1–2 hours |
| Input parsing + validation | 3–5 hours |
| Pretty output / table formatting | 2–3 hours |
| Writing tests for a module | 2–4 hours |
| README + docs | 4–6 hours |

> ⚠️ **Always count "understanding time"** : AI writes in seconds but *you* learn in hours.

## 4. The 60% Rule
Plan to finish **60% of your wish list**. Plans always expand. If you can finish everything comfortably, the project is probably too small; if you cannot finish the Must-haves in 2 weeks, it is too big.

## 5. Scope Cutting Rules (When Behind)
Cut in this order:
1. Could-haves
2. Fancy UI/colors
3. Secondary algorithms
4. Advanced error cases
5. **Never cut:** core feature, tests for the core, documentation, understanding
