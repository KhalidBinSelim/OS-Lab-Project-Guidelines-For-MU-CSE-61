# 03 · Using AI Responsibly

> **Policy:** AI is allowed. **Not understanding is not.**
> If you cannot explain a line, it is not your code.

## 1. Why This Matters
AI can write a working scheduler in 30 seconds. But in the presentation you may be asked:
*"Why is this loop condition `<` and not `<=`?"* · *"What happens if I change this to 3?"* · *"Rewrite this function without AI."*

AI makes **code** cheap. It does not make **understanding** cheap. Your marks come from understanding.

---

## 2. The 7-Step Understanding Workflow (use for every AI-generated piece)

| Step | Action |
|------|--------|
| 1. **Prompt** | Ask for **one small piece** (a function), with context |
| 2. **Read** | Read all of it **slowly**, line by line |
| 3. **Explain** | Ask AI: *"Explain each line like I'm a beginner"* |
| 4. **Trace** | **Hand-trace** it on paper with a small example |
| 5. **Modify** | Change something (a value, a condition) and **predict** the result |
| 6. **Test** | Run it, break it, fix it |
| 7. **Log** | Write the AI log entry + code explanation |

Short form: **Prompt → Read → Explain → Trace → Modify → Test → Log.**

### The "Explain-Back" Test ✅
Before committing, close the AI chat and explain the code **aloud** to a teammate (or a rubber duck) **without looking**. If you get stuck, you don't own it yet.

---

## 3. Good Prompting for OS Projects

### ❌ Bad
> "Write a complete mini OS project."

### ✅ Good
> "I'm building a CPU scheduling simulator in C for an OS lab. I have `struct PCB { int pid, arrival, burst, remaining; }`. Write a function `void round_robin(PCB *p, int n, int quantum)` that fills `start`, `finish` times. Use a circular ready queue. Add comments explaining each step. Don't print anything inside the function."

### Prompt Recipe
1. **Context:** language, OS, what the project is
2. **Existing code/structs** it must fit
3. **Exact task:** one function/module
4. **Constraints:** no global variables, check errors, C11, comments
5. **Ask for explanation** and **edge cases**

### Useful Learning Prompts
- "Explain `fork()` like I'm new to C. Draw what happens to memory."
- "Give me 3 different test inputs for this function, including edge cases, with expected outputs."
- "What are the possible bugs in this code? Don't fix them yet; list them."
- "Explain this line by line: ..."
- "Quiz me with 5 viva questions on this module. Wait for my answer before correcting."
- "Why did you choose a `while` loop here instead of `for`?"

## 4. Typical AI Mistakes in OS Code (Check For These!)

| Mistake | Why dangerous |
|---------|---------------|
| Race conditions (no mutex, or wrong lock order) | Random wrong results |
| Missing `wait()` / zombie processes | Resource leaks |
| Child continues after failed `exec` | Duplicate shell loops |
| Not closing pipe ends | Program hangs |
| Buffer overflow (`scanf("%s")`, `strcpy`) | Crashes / security |
| Memory leaks, double free | Crashes |
| Off-by-one in arrays/frames | Wrong simulation results |
| Using Windows-only/obsolete APIs | Does not compile on Linux |
| Wrong algorithm details (e.g., SRTF tie-breaking, SCAN direction) | Wrong output that *looks* right |
| Hallucinated functions/headers | Compile errors |
| Over-complicated code | You can't explain it |

> **Never trust AI output blindly. Verify with hand calculations from your textbook examples.**

## 5. Rules for Your Repository

1. ✅ Every AI-assisted file/function gets an entry in [`docs/AI_USAGE_LOG.md`](../templates/AI_USAGE_LOG_TEMPLATE.md).
2. ✅ Every source file gets an entry in [`docs/CODE_EXPLANATIONS.md`](../templates/CODE_EXPLANATION_TEMPLATE.md) written **in your own words**.
3. ✅ Mark AI-assisted files in the header comment.
4. ✅ Commit small pieces; do not paste 800 lines in one commit.
5. ❌ Do not use AI to write your explanations/answers for Q/A — you will not be able to defend them.
6. ❌ Do not hide AI use. Honest, well-understood use is fine; hidden or unexplained use is a problem.

---

## 6. Understanding Checklist (Per Module)

- [ ] I can state in one sentence what this module does.
- [ ] I can name every variable's purpose.
- [ ] I can trace the main function on a small input on paper.
- [ ] I know what happens on invalid input.
- [ ] I can say which **OS concept** each important line demonstrates.
- [ ] I can rewrite the core logic in pseudocode from memory.
- [ ] I can predict the output if one parameter changes.
- [ ] A teammate has heard my explanation.

---

## 7. Live-Change Drill (Practice Weekly)
Teammate picks a random line and says:
- "Change the quantum to 4, what is the new Gantt chart?"
- "Add a new field to the struct and print it."
- "Make this algorithm preemptive."
- "Why would removing this `close()` hang the program?"

If you can do these, you are ready.

---

## 8. What Examiners May Do
- Ask you to **scroll to any file** and explain it
- Ask you to **modify code live**
- Ask **why not** an alternative approach
- Ask the **OS theory** behind a feature
- Ask what you would do **without AI**

Prepare accordingly!
