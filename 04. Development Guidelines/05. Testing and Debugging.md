# 05 · Testing and Debugging

## 1. Why Test OS Projects?
OS-style code (processes, threads, memory) fails in sneaky ways: crashes, hangs, leaks, "works sometimes". Testing is your safety net **and** evidence for marks.

## 2. Test Levels

| Level | What | How |
|-------|------|-----|
| Unit | One function (e.g., `calculate_waiting_time`) | C test file with `assert()` |
| Integration | Modules together | Run program with input file, compare to expected output |
| System / demo | Full workflow | Scripted scenario from the demo |
| Stress | Large or weird input | 1000 processes, empty input, huge numbers |
| Memory | Leaks / invalid access | `valgrind`, AddressSanitizer |
| Concurrency | Races/deadlocks | Run 50–100 times, use ThreadSanitizer |

## 3. Simple Unit Test Example
```c
// tests/test_metrics.c
#include <assert.h>
#include "metrics.h"

int main(void) {
    assert(turnaround_time(/*arrival*/2, /*finish*/9) == 7);
    assert(waiting_time(/*turnaround*/7, /*burst*/4)  == 3);
    return 0;
}
```
Compile and run: `gcc -Iinclude tests/test_metrics.c src/metrics.c -o build/test_metrics && ./build/test_metrics`

## 4. Output-Comparison Tests (Easy and Powerful)
```
tests/
├── run_tests.sh
├── case01.in
├── case01.expected
├── case02.in
└── case02.expected
```
```bash
#!/bin/bash
# tests/run_tests.sh
pass=0; fail=0
for f in tests/case*.in; do
  base="${f%.in}"
  ./build/app < "$f" > /tmp/out.txt 2>&1
  if diff -q /tmp/out.txt "$base.expected" > /dev/null; then
    echo "PASS $base"; pass=$((pass+1))
  else
    echo "FAIL $base"; fail=$((fail+1))
  fi
done
echo "Passed: $pass  Failed: $fail"
[ $fail -eq 0 ]
```
> Calculate expected outputs **by hand or from your textbook**, not from your own program. Otherwise you test nothing.

## 5. What To Test (Checklist)
- [ ] Normal input
- [ ] Minimum input (1 process / 1 frame / 1 request)
- [ ] Empty or missing file
- [ ] Invalid values (negative, letters, too large)
- [ ] Ties (same arrival time, same priority)
- [ ] Boundary values (0, max array size)
- [ ] Repeated runs (state properly reset)
- [ ] Textbook examples with known answers
- [ ] Interrupt (`Ctrl+C`) and cleanup (processes, IPC)

## 6. Debugging Toolbox

### 6.1 Print Debugging
`fprintf(stderr, "DEBUG: i=%d remaining=%d\n", i, remaining);` — use a `DEBUG` macro so you can turn it off.

### 6.2 `gdb`
```bash
gcc -g -O0 src/*.c -o app
gdb ./app
(gdb) break scheduler.c:42
(gdb) run < examples/set1.txt
(gdb) next / step / continue
(gdb) print p[i]
(gdb) backtrace
(gdb) watch remaining
```
For `fork`: `set follow-fork-mode child`.

### 6.3 `valgrind`
```bash
valgrind --leak-check=full --show-leak-kinds=all ./app < input.txt
```
Fix **all** "invalid read/write" first; then leaks.

### 6.4 Sanitizers (fast)
```bash
gcc -g -fsanitize=address,undefined src/*.c -o app_asan
gcc -g -fsanitize=thread src/*.c -pthread -o app_tsan   # races
```

### 6.5 `strace` (system calls)
```bash
strace -f -o trace.txt ./myshell
```
Great for seeing whether `fork/execve/pipe/dup2` happen as you believe.

### 6.6 Hangs
- `ps aux | grep app` then `cat /proc/<pid>/stack` or `gdb -p <pid>` → `bt`
- Hung pipe? Check all unused ends are closed.
- Hung semaphore? Print before/after each `sem_wait`.

## 7. Debugging Method (Scientific)
1. **Reproduce** the bug reliably.
2. **Shrink** the input to the smallest failing case.
3. **Hypothesize** the cause.
4. **Test** the hypothesis (print / debugger).
5. **Fix** one thing.
6. **Add a test** so it never returns.
