# 04 · Hackathon-Style Sprint Playbook

Hackathons teach one skill above all: **ship a working demo under time pressure.** Use the same mindset for your 1-month OS project.

## 1. Core Mindset

| Hackathon rule | OS project version |
|----------------|--------------------|
| Demo > slides | A working 3-minute demo beats a perfect design document |
| MVP first | Build the smallest thing that shows the OS concept |
| Timebox everything | "If it is not working in 2 hours, simplify or ask for help" |
| Cut scope, not quality | Fewer features, each working and tested |
| Always have a backup | Screenshots, recording, pre-loaded input files |
| Tell a story | Problem → OS concept → solution → demo → lessons |

## 2. The Sprint Structure
Use **weekly sprints** inside the 4-week plan.

**Sprint Planning (Monday, 30 min):** pick issues, assign owners, define the "demoable goal".
**Daily Standup (10 min):** what I did · what I will do · what blocks me.
**Sprint Demo (Friday, 30 min):** show working features to your teammates.
**Retrospective (10 min):** what went well · what to change.

## 3. Vertical Slices, Not Layers
Build thin end-to-end paths first:
```
Day 1:  hard-coded input  →  one algorithm  →  print result
Day 3:  file input        →  two algorithms →  formatted table
Day 6:  validation        →  five algorithms→  charts + metrics
```
You always have *something that runs*.

## 4. Timeboxing Rules
- **Stuck > 45 minutes?** Explain the problem to a teammate (rubber duck).
- **Stuck > 2 hours?** Simplify the approach or ask the instructor.
- **Feature takes 2× the estimate?** Re-scope it immediately.
- **Perfectionism trap:** pretty output comes *after* correct output.

## 5. Branch-Per-Feature Flow
```
main  ───●────────────●─────────●───►   (always runnable)
          \          /         /
           feature/fcfs ──────/
```

## 6. Definition of Done (per feature)
A feature is **done** only when:
- [ ] It compiles with zero warnings
- [ ] It passes its test cases
- [ ] It handles bad input
- [ ] Another teammate reviewed it (PR)
- [ ] It is explained in `CODE_EXPLANATIONS.md`
- [ ] It is mentioned in the README if user-facing

## 7. Feature Freeze
**Day 24** (end of Week 3): no new features. Only:
- Bug fixes
- Tests
- Docs
- Demo prep

Most failed presentations come from last-minute features.

## 8. Demo-Driven Development
Write the **demo script first**. Then build features in the order the demo needs them. Anything not in the demo is "Could-have".

## 9. Risk Management

| Risk | Early warning | Mitigation |
|------|---------------|------------|
| Idea too big | MVP not working at day 14 | Cut features; keep the core |
| Teammate disappears | No commits for a week | Redistribute tasks, inform instructor |
| AI code you can't explain | You can't trace it | Rewrite simpler, ask AI to explain, or discard |
| Merge conflicts at the end | Long-lived branches | Merge small and often |
| Demo crashes | Untested edge cases | Test with fresh clone; prepare recording |
| Machine-specific bug | "Works on my laptop" | CI-like check: clone and build on another machine |

## 10. Hackathon Habits That Pay Off
1. **Commit early, commit often** : small commits = safe progress.
2. **Automate** : `make test` should run everything.
3. **Seed data** : keep good example inputs ready.
4. **Make failure visible** : clear error messages beat silent crashes.
5. **One source of truth** : one issue board, one README.
6. **Sleep** : a rested brain debugs faster than a tired one.
7. **Practice the pitch out loud** : at least twice.
