# 02 · Project Structure and Coding Standards

## 1. Recommended Repository Layout (for **your** project repo)

```
your-project/
├── README.md                  # How to build, run, demo
├── LICENSE
├── Makefile
├── .gitignore
├── src/                       # all source (.c)
├── include/                   # headers (.h)
├── tests/                     # test scripts + expected outputs
├── examples/                  # sample inputs
├── docs/
│   ├── PROPOSAL.md
│   ├── DESIGN.md              # architecture + diagrams
│   ├── OS_CONCEPTS.md         # theory used in the project
│   ├── USER_GUIDE.md
│   ├── CODE_EXPLANATIONS.md   # file-by-file explanation
│   ├── AI_USAGE_LOG.md
│   ├── TEST_REPORT.md
│   ├── progress/              # weekly reports
│   └── slides.pdf
└── build/                     # compiled output (git-ignored)
```

## 2. Makefile Starter
```makefile
CC      = gcc
CFLAGS  = -Wall -Wextra -std=c11 -g -Iinclude
LDFLAGS = -pthread
SRC     = $(wildcard src/*.c)
OBJ     = $(SRC:src/%.c=build/%.o)
TARGET  = build/app

all: $(TARGET)

$(TARGET): $(OBJ)
	$(CC) $(OBJ) -o $@ $(LDFLAGS)

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build

debug: CFLAGS += -fsanitize=address,undefined
debug: clean all

test: all
	bash tests/run_tests.sh

clean:
	rm -rf build

.PHONY: all debug test clean
```
> Lines starting with `TAB>` above must begin with a real **Tab** character in your Makefile (not spaces).

## 3. Coding Standards (Simple but Strict)

### Naming
| Item | Style | Example |
|------|-------|---------|
| Files | `snake_case.c` | `page_table.c` |
| Functions / variables | `snake_case` | `calculate_waiting_time` |
| Constants / macros | `UPPER_SNAKE` | `MAX_PROCESSES` |
| Structs | `PascalCase` or `snake_case_t` | `Process`, `frame_t` |

### Rules
1. **One function = one job**, ideally under ~40 lines.
2. **Meaningful names:** `waiting_time`, not `wt2`.
3. **No magic numbers:** use `#define` / `enum`.
4. **Check return values** of every system call (`fork`, `pipe`, `open`, `malloc`, `read`, `write`).
5. **Free** what you `malloc`; close what you open.
6. **Comment the "why",** not the "what".
7. **No giant `main()`**: split into modules.
8. **Compile clean:** zero warnings with `-Wall -Wextra`.
9. **Format automatically:** `clang-format -i src/*.c include/*.h`.

### Error Handling Pattern
```c
pid_t pid = fork();
if (pid < 0) {
    perror("fork failed");
    exit(EXIT_FAILURE);
}
```

### Header Comment for Every File
```c
/*
 * File:    fifo.c
 * Purpose: FIFO page replacement algorithm
 * Author:  <name>   (AI-assisted: yes/no — see docs/AI_USAGE_LOG.md)
 * OS concept: Page replacement (Silberschatz ch. 10)
 */
```

### Comment Style Example
```c
/* Evict the page that has been in memory the longest (front of queue). */
victim = frames[fifo_index];
fifo_index = (fifo_index + 1) % num_frames;   /* circular queue */
```

## 4. Design Principles for OS Projects
- **Separate logic from I/O:** algorithms should not call `printf`/`scanf` directly; return results and let a display function print them (makes testing easy).
- **Use function pointers** for interchangeable algorithms (scheduler, replacement).
- **Keep global variables to a minimum.**
- **Make state explicit** (structs passed around) so you can reset between runs.

## 5. Security & Safety Basics
- Never use `gets()`; avoid `strcpy`/`sprintf` → use `fgets`, `snprintf`, `strncpy` carefully.
- Validate all user input (range, type, length).
- Don't run commands built from raw user input in `system()`.
- Do not hard-code absolute paths on your own machine.
