# Idea 06 · Mini File System (Virtual Disk + Shell Commands)

## 1. Overview
Implement a small file system inside **one big file** (`disk.img`) acting as a virtual disk. Users interact through commands like `mkdir`, `create`, `write`, `read`, `ls`, `rm`.

**Difficulty:** ⭐⭐⭐ · **Language:** C · **Best for:** teams who want to understand file-system internals deeply

## 2. OS Concepts Covered
Blocks · superblock · inode · directory entry · free-space bitmap · allocation methods (contiguous/linked/indexed) · file metadata · persistence · fragmentation

## 3. Features

### Must
- Create/format a virtual disk (e.g., 1 MB, 512-byte blocks)
- Single-level or root-only directory
- Commands: `format`, `create`, `write`, `read`, `ls`, `delete`, `info`
- Free-block tracking (bitmap) and error on "disk full"
- Persistence: reopen `disk.img` and files still exist

### Should
- Hierarchical directories: `mkdir`, `cd`, `pwd`, `rmdir`
- Indexed allocation (inode with direct block pointers)
- File metadata: size, created time, permissions
- `df`-like usage report and **fragmentation view**

### Could
- Indirect block pointer for large files
- Hard links / symbolic links
- Simple permissions check (`chmod`, owner)
- Compare contiguous vs linked vs indexed behavior with a demo

## 4. Suggested Design
```
Disk layout:
[ Superblock | Inode bitmap | Block bitmap | Inode table | Data blocks ]
```
```
src/
├── disk.c        # read_block / write_block on disk.img
├── fs.c          # format, mount, inode alloc/free
├── dir.c         # directory operations
├── file.c        # create/read/write/delete
├── shell.c       # command interpreter
└── bitmap.c
```
`struct Inode { int size; int type; int direct[10]; time_t ctime; }`

## 6. Demo Scenario
```
fs> format 1024
fs> create notes.txt
fs> write notes.txt "hello operating system"
fs> ls
fs> info notes.txt     # shows inode and block numbers
fs> exit
$ ./fs disk.img        # reopen → files are still there
```
Show a hex dump (`xxd disk.img | head`) to prove it is a real on-disk structure.

## 7. You Must Be Able To Explain
- What the superblock stores and why it must be read first
- How a file name becomes data: directory entry → inode → block pointers → blocks
- How bitmap allocation and freeing works (bit operations!)
- What happens on delete (are data blocks erased?)
- Why a maximum file size exists with direct pointers only

## 8. Pitfalls
- Bit-manipulation bugs in the bitmap
- Struct padding changes size on disk → use fixed-size fields and check `sizeof`
- Not flushing writes → data lost on exit
- Overwriting metadata blocks by wrong block indexing

## 9. Exceptions
Compression flag · simple file encryption · "undelete" · journaling-lite log · visual map of used/free blocks
