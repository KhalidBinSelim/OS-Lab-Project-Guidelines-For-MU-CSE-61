# Idea 09 · IPC Job Queue Server (Message Queue + Shared Memory)

## 1. Overview
A small **multi-process system**: a *producer/client* program submits jobs (e.g., "compute factorial", "count words in file") to a **server** that distributes them to **worker processes**. Communication uses **IPC mechanisms** learned in lab.

**Difficulty:** ⭐⭐⭐ · **Language:** C on Linux

## 2. OS Concepts Covered
Process creation · message queues · shared memory · semaphores for protecting shared memory · pipes · signals · job scheduling · cleanup of IPC resources

## 3. Features

### Must
- `server` creates a **message queue** (System V `msgget` or POSIX `mq_open`)
- `client` submits a job message (type, payload, priority)
- At least 2 **worker processes** (`fork`) that receive and execute jobs
- Results returned to client (via second queue or shared memory)
- Clean shutdown that **removes IPC objects**

### Should
- Shared-memory **status board** (jobs pending/running/done) protected by a semaphore
- Job priorities (message type as priority)
- Graceful `SIGINT` handling
- Log file with timestamps, PIDs, job IDs

### Could
- Dynamic worker count (spawn/kill based on load)
- Compare IPC mechanisms (pipe vs queue vs shared memory) on speed
- Job timeout and retry
- Simple text dashboard reading the shared status board

## 4. Suggested Design
```
Client(s) ──msg queue──► Server ──► Worker 1..N
    ▲                        │
    └────── results ◄────────┘      Shared memory: status board (+ semaphore)
```
```
src/
├── common.h      # message struct, keys, constants
├── server.c
├── worker.c
├── client.c
├── shm_board.c   # shared memory + semaphore wrapper
└── monitor.c
```

## 6. Demo Scenario
1. Start server with 3 workers.
2. Start 2 clients in two terminals, submit several jobs.
3. Show dashboard: jobs spread across workers.
4. Press `Ctrl+C` on server → run `ipcs` → **no leftover IPC objects**.

## 7. You Must Be Able To Explain
- What a message queue stores and how `msgtype` selects messages
- Shared memory is fastest but **needs synchronization** — why?
- Why `ipcrm`/`msgctl(IPC_RMID)` cleanup is needed
- Fork model: which process owns which resource
- Differences: pipe vs message queue vs shared memory

## 8. Pitfalls
- Leaving stale IPC objects (`ipcs` shows them; old keys cause bugs)
- Message struct must begin with `long mtype`
- Race conditions on the shared board without a semaphore
- Zombie workers (no `wait`)
- Hard-coded keys colliding with other teams on shared machines → use `ftok`

## 9. Exceptions
Priority aging · job dependency ("run B after A") · worker crash recovery · web-style status page generated as HTML
