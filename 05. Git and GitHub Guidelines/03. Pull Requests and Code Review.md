# 03 · Pull Requests and Code Review

## 1. Why PRs?
- Catch bugs before they reach `main`
- **Teach teammates** your code (this is great viva preparation!)
- Leave a visible record of discussion and decisions

## 2. How To Open a Good PR
1. Push your branch: `git push -u origin feature/round-robin`
2. On GitHub click **Compare & pull request**
3. Fill the PR template (auto-loaded from `.github/PULL_REQUEST_TEMPLATE.md`)
4. Link the issue: `Closes #7`
5. Assign a **reviewer** (not yourself)
6. Keep PRs **small** (< ~300 lines changed if possible)

### PR Description Example
```markdown
## What
Adds Round Robin scheduling with configurable quantum.

## Why
Required Must-have feature F3 (closes #7).

## How I tested
- examples/set1.txt, quantum 2 → matches textbook Gantt chart
- valgrind: no leaks

## OS concept
Time-sharing, preemption, context switch.

## AI assistance
Yes — initial skeleton generated; I rewrote queue handling. See AI_USAGE_LOG entry 5.
```

## 3. Reviewer Checklist
- [ ] Does it build with no warnings?
- [ ] Does it do what the issue says?
- [ ] Can **I** explain this code after reading it? (If no → ask the author!)
- [ ] Are errors handled (return values, bad input)?
- [ ] Memory/resources freed/closed?
- [ ] Names and comments clear?
- [ ] Tests added/updated?
- [ ] Docs updated (`CODE_EXPLANATIONS.md`)?

## 4. How To Review Kindly and Usefully
- Comment on **code**, not the person.
- Ask questions: *"What happens if `n` is 0 here?"*
- Suggest alternatives with reasons.
- Mark minor style points as `nit:`.
- Approve only when you **understand** the change.

## 5. Responding To Review
- Reply to every comment (fixed / explain why not).
- Push fixes to the same branch; the PR updates automatically.
- Do not take comments personally — reviews improve your Q/A answers.

## 6. Merge Rules
- Prefer **Squash and merge** for small features (clean history) or **Merge commit** to preserve detail — choose one and stay consistent.
- Delete the branch after merging.
- Pull `main` locally afterwards: `git switch main && git pull`.

## 7. Cross-Review Rule for This Project
Every PR must be reviewed by a **different** teammate. The reviewer must be able to give a **30-second explanation** of the PR in the weekly teach-back.
