# 01 · Project Overview and Rules

## 1. What Is the OS Lab Project?

Instead of a final lab exam, you will complete **one OS-related project** during the semester (about **4 weeks** of focused work). You will:

1. **Build** a working software project that demonstrates real Operating System concepts.
2. **Submit** it through a GitHub repository.
3. **Present** it (live demo + slides).
4. **Answer questions** (Q/A / viva) about the design, the code, and the OS theory behind it.

## 2. What Counts as an "OS Project"?

An OS project **implements, simulates, or uses** core operating-system mechanisms. Examples:

| Type | Meaning | Example |
|------|---------|---------|
| **Simulator** | You model an OS component in software | CPU scheduler simulator, page replacement simulator |
| **System-call tool** | You use real OS APIs (`fork`, `exec`, `pipe`, `pthread`, `mmap`) | Mini shell, IPC job queue |
| **System inspector** | You read live OS information | Process monitor using `/proc` |
| **Mini subsystem** | You build a simplified version of an OS part | In-memory file system |

**Not expected:** writing a real bootable kernel from scratch. (You may mention it as "future work".)

## 3. Core Rules

### 3.1 Originality
- Your project must be **your team's work**, built in **your own GitHub repo**.
- Copying another team's repo or an online project and renaming it is **plagiarism**.
- Two teams may choose the same *idea*, but the **code, design, and extra features must differ**.

### 3.2 AI Usage Policy
AI tools (ChatGPT, Claude, Copilot, etc.) are **allowed**, under these conditions:

1. You must **understand every line** you submit.
2. You must keep an **AI Usage Log** ([template](../templates/AI_USAGE_LOG_TEMPLATE.md)).
3. You must be able to **explain it, modify it, and debug it live**.
4. AI-generated code that you cannot explain will be treated as **if you did not write it**.

### 3.3 Individual Accountability
Even in a team, **every member** must:
- Make real commits in GitHub (the commit history is visible evidence).
- Understand the **whole** project, not only their own module.
- Be ready to answer questions about **any** part.

### 3.4 Platform & Language
- **Recommended:** C on Linux (Ubuntu / WSL2). This matches what we used in the OS labs (`fork`, pipes, message queues, shared memory, `pthread`).
- Python is acceptable for **simulators/visualizers** (not for system-call-heavy ideas). 
- The project must build and run from the instructions in your README on a **clean Linux machine**.
